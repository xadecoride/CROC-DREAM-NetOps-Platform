# CROC DREAM — NetOps Platform

**Платформа централизованного управления и мониторинга гетерогенной сетевой инфраструктуры (NetOps Platform)**

**Команда:** CROC DREAM

**Целевой стек:** Python 3.11+, FastAPI, Celery, Redis, PostgreSQL, Nornir 3, Scrapli, hier_config, Jinja2, Vite + React, Containerlab, Prometheus, Grafana

## 1. Архитектурная концепция платформы

### 1.1. Базовые принципы решения

При эксплуатации гетерогенной сети (состоящей из оборудования разных производителей) ключевыми проблемами являются различия в синтаксисе команд, человеческий фактор при ручной настройке через консоль и так называемый дрейф конфигурации (*Config Drift*) — несанкционированные правки, внесенные напрямую в обход общих правил.

Предлагаемая платформа решает эти проблемы за счет перехода к программно-управляемой модели:

- **Единый источник параметров (Source of Truth).** Сетевые инженеры описывают не конкретные вендорские команды, а сетевые намерения (*Intent*) в виде понятных структурированных файлов YAML. Все изменения проходят версионирование в Git.
- **Абстракция над вендорами.** Логика настройки протоколов (BGP, интерфейсы, адресация, списки доступа) отделена от синтаксиса конкретной операционной системы. Специализированные шаблонизаторы переводят абстрактную модель в точные команды для Cisco IOS-XE, Arista EOS или Huawei VRP.
- **Иерархический анализ различий (Hierarchical Diff).** Вместо небезопасной перезаписи всего файла конфигурации система забирает текущий рабочий конфиг (*running-config*), строит дерево параметров и рассчитывает минимально необходимый точечный патч для наката (`remediation_config`), а также зеркальный набор команд для быстрого отката назад (`rollback_config`).
- **Транзакционность и безопасность раскатки.** Любое изменение на оборудовании применяется через механизм сессий с подтверждением по таймеру (*commit confirmed*). Если после применения конфигурации сетевые тесты фиксируют сбой связности или падение BGP-маршрутизации, система отменяет коммит и возвращает сеть в рабочее состояние без участия человека.
- **Непрерывный комплаенс.** Фоновые роботы регулярно опрашивают оборудование, сверяют его реальный конфиг с эталоном из Git и сигнализируют инженерам при обнаружении любых расхождений.

## 2. Детальное техническое задание на MVP

### 2.1. Модуль инвентаризации и модели данных (Source of Truth)

Модуль отвечает за хранение информации об инфраструктуре и целевых сетевых параметрах.

#### 1. Модель сетевого устройства

Каждое устройство описывается в реляционной базе данных и файле инвентаря со следующими атрибутами:

| Атрибут | Описание |
|---|---|
| `id` | Уникальный числовой или строковый идентификатор |
| `hostname` | Сетевое имя устройства (например, `leaf-1.croc.lab`) |
| `management_ip` | IPv4-адрес для подключения по сети управления |
| `management_port` | TCP-порт службы SSH (по умолчанию 22 или кастомный проброшенный порт стенда) |
| `platform` | Идентификатор сетевой операционной системы: `cisco_iosxe`, `arista_eos`, `huawei_vrp` |
| `role` | Функциональное назначение в топологии: `spine`, `leaf`, `border` |
| `auth_profile` | Ссылка на учётную запись (логин и пароль для SSH-сессии) |
| `status` | Текущий статус комплаенса: `IN_SYNC`, `DRIFT_DETECTED`, `UNREACHABLE`, `IN_PROGRESS` |

#### 2. Декларативная модель сетевых намерений (YAML)

Все целевые настройки хранятся в репозитории Git в виде структурированных файлов. Модель описывает три основных функциональных блока:

**Блок интерфейсов (`interfaces`)**

| Поле | Описание |
|---|---|
| `name` | Физическое имя порта (например, `GigabitEthernet1` или `Ethernet1`) |
| `description` | Текстовое назначение линка (например, `Uplink to Spine-1`) |
| `enabled` | Статус порта (`true` / `false`) |
| `mode` | Режим работы: `l3` для маршрутизируемых портов, `l2` для коммутируемых |
| `ipv4_address` | IP-адрес интерфейса с маской (например, `10.10.0.1/31`) |
| `mtu` | Размер MTU (по умолчанию 1500 или 9000 для Jumbo Frames) |

**Блок динамической маршрутизации (`bgp`)**

| Поле | Описание |
|---|---|
| `asn` | Номер локальной автономной системы (например, `65001`) |
| `router_id` | Уникальный идентификатор маршрутизатора в формате IPv4 (например, `10.255.0.1`) |
| `neighbors` | Перечень BGP-соседей |

Поля каждого соседа (`neighbors`):

- `peer_ip` — IP-адрес соседа;
- `remote_asn` — номер автономной системы соседа;
- `description` — текстовое описание пиринга;
- `password` — ключ аутентификации MD5 (опционально);
- `announced_prefixes` — список подсетей, анонсируемых в BGP (например, `["10.255.0.1/32"]`).

**Блок фильтрации трафика (`acls`)**

- `name` — имя списка доступа;
- `rules` — упорядоченный список правил:
  - `sequence` — порядковый номер правила;
  - `action` — действие: `permit` или `deny`;
  - `protocol` — сетевой протокол: `ip`, `tcp`, `udp`, `icmp`;
  - `source` — подсеть источника или `any`;
  - `destination` — подсеть назначения или `any`.

#### 3. Валидация входных данных

Перед сохранением или передачей данных в генератор бэкенд выполняет строгую проверку через Pydantic:

- проверка корректности формата IP-адресов и длин сетевых масок;
- контроль отсутствия пересечений IP-адресов на интерфейсах одного устройства;
- проверка диапазона номеров автономных систем (ASN от 1 до 4294967295);
- контроль уникальности BGP Router ID в рамках всей инфраструктуры.

В случае ошибки модуль возвращает структурированный ответ с указанием проблемного поля и блокирует запуск пайплайна.

### 2.2. Модуль шаблонизации и вендорной абстракции

Модуль преобразует абстрактные параметры из YAML в готовые команды командной строки (CLI) для конкретного сетевого оборудования.

#### 1. Структура каталога шаблонов

Шаблоны Jinja2 хранятся в изолированных директориях по вендорам:

```text
templates/cisco_iosxe/
├── base.j2          # системные параметры (hostname, domain, timeouts)
├── interfaces.j2    # настройка L3/L2 портов, MTU, IP-адресов и описаний
└── bgp.j2           # процесс router bgp, объявление соседей, активация
                     # в address-family ipv4 unicast, next-hop-self, send-community

templates/arista_eos/
├── base.j2          # базовые параметры EOS
├── interfaces.j2    # директивы no switchport, назначение IP и MTU
└── bgp.j2           # процесс router bgp, назначение router-id, объявление
                     # пиров в neighbor ... remote-as, активация в address-family
```

#### 2. Нормализация текста и очистка артефактов

Сетевые операционные системы при выводе конфигурации добавляют динамические маркеры. Движок генерации и очистки производит обязательную фильтрацию:

- удаление системных баннеров и временных меток сборки (`Building configuration...`, `Current configuration : 1234 bytes`);
- фильтрация динамических сертификатов и криптографических ключей, которые генерируются операционной системой локально;
- приведение пробелов и отступов к единому стандарту вендора для исключения ложных различий при дифференциальном анализе.

### 2.3. Спецификация API бэкенда

Серверная часть на FastAPI предоставляет следующие ключевые эндпоинты для работы веб-интерфейса и внешних систем:

| Метод | URL эндпоинта | Назначение | Тело запроса / Параметры | Формат ответа |
|---|---|---|---|---|
| `GET` | `/api/v1/devices` | Получение списка всех сетевых устройств | Фильтры по статусу, роли, платформе | JSON-список объектов устройств с текущими статусами |
| `GET` | `/api/v1/devices/{id}` | Детальная информация по конкретному устройству | Идентификатор `id` в URL | Полная карточка устройства, сетевые параметры и время последней проверки |
| `POST` | `/api/v1/jobs/dry-run` | Запуск пробного прогона (генерация и расчет diff) | `{"device_ids": [1, 2], "intent_source": "git_main"}` | Идентификатор созданной фоновой задачи (`job_id`) |
| `GET` | `/api/v1/jobs/{id}` | Проверка статуса выполнения задачи | Идентификатор `job_id` в URL | Статус (`PENDING`, `RUNNING`, `SUCCESS`, `FAILED`), прогресс (в %), логи |
| `GET` | `/api/v1/jobs/{id}/diff` | Получение рассчитанной разницы конфигурации | Идентификатор `job_id` в URL | JSON со списками: `running_config`, `intended_config`, `remediation_patch`, `rollback_patch` |
| `POST` | `/api/v1/jobs/deploy` | Запуск транзакционного применения изменений | `{"job_id": "...", "confirmed_by": "operator_name"}` | Новый `job_id` для процесса деплоя |
| `POST` | `/api/v1/drift/scan` | Запуск внеочередной проверки дрейфа конфигурации | Опциональный список `device_ids` (по умолчанию все) | Идентификатор задачи сканирования |
| `GET` | `/api/v1/drift/report` | Сводный отчет о найденных расхождениях | Фильтр по дате и статусу | Список устройств с обнаруженным дрейфом и деталями различий |
| `POST` | `/api/v1/drift/remediate` | Автоматическое приведение устройства к эталону | `{"device_id": 1}` | Идентификатор задачи наката компенсирующего патча |

### 2.4. Пайплайн раскатки конфигураций (Network CI/CD)

Конвейер применения изменений строится по принципу изолированной транзакции и гарантирует безопасность сети на каждом этапе:

#### Этап 1. Статический контроль (Pre-flight Lint)

- Проверка синтаксиса и структуры YAML-моделей по схемам Pydantic.
- Алгоритмический контроль дублирования IP-адресов и уникальности BGP Router ID.

**Результат этапа:** при выявлении ошибок транзакция завершается аварийно (статус `FAILED`) без обращения к сетевому оборудованию; при успешной проверке выполняется переход к Этапу 2.

#### Этап 2. Холостой прогон (Dry-run)

1. Воркер Celery через Scrapli параллельно подключается к оборудованию и снимает текущий `running-config`.
2. Нормализация текстов (удаление динамических меток времени, счетчиков байтов и баннеров).
3. Иерархический анализ через библиотеку hier_config:
   - расчет минимального набора команд наката (`remediation_config`);
   - формирование зеркального набора команд безопасного возврата назад (`rollback_config`).
4. Передача рассчитанной разницы в двухпанельный Side-by-Side Diff Viewer веб-панели.
5. Анализ рисков через LLM-ассистента и вывод карточки с текстовым резюме планируемых изменений.
6. Пайплайн блокируется до явного нажатия кнопки **«Применить изменения»** (*Manual Approval*) дежурным инженером.

#### Этап 3. Транзакционный деплой и контроль здоровья (Health-Check)

1. Запуск **Pre-Check** тестов: фиксация рабочего состояния BGP-соседей и линков.
2. Инициализация безопасной сессии на оборудовании:
   - директива `commit confirmed 180` на Cisco IOS-XE;
   - открытие транзакционной сессии `configure session` на Arista EOS.
3. Доставка набора команд `remediation_config` через драйвер Scrapli.
4. Запуск серии **Post-Check** тестов: проверка перехода BGP в статус `Established`, отсутствия дропов на интерфейсах и сквозного ping.
5. **Условие подтверждения:** если все проверки пройдены успешно, отправляется подтверждающий коммит (`commit` на Cisco, `commit session` на Arista), транзакция переходит в статус `SUCCESS`.
6. **Условие отката:** если зафиксирован сбой тестов или потеря связи, платформа блокирует коммит, инициируя аппаратный откат по таймеру, либо принудительно накатывает файл `rollback_config`.

### 2.5. Модуль отслеживания дрейфа конфигурации (Config Drift Engine)

**Регламент фоновой проверки:** планировщик Celery Beat каждые 15 минут запускает фоновую задачу инспекции устройств.

**Алгоритм сопоставления:**

1. Воркер скачивает актуальный `running-config` с целевого устройства.
2. Вызывается библиотека hier_config, куда передается снятый рабочий конфиг и эталонный конфиг из репозитория Git.
3. Библиотека формирует список строк, которые присутствуют на оборудовании, но отсутствуют в эталоне (неавторизованные команды), а также список отсутствующих эталонных настроек.

**Классификация состояния:**

| Статус | Описание |
|---|---|
| `IN_SYNC` | Расхождений между эталоном и реальным состоянием не выявлено |
| `DRIFT_DETECTED` | Обнаружены неавторизованные изменения (сохраняются точные строки различий) |
| `UNREACHABLE` | Устройство недоступно по сети управления |

**Устранение дрейфа (Remediation):** в веб-интерфейсе оператору доступна кнопка **«Устранить дрейф»**. При нажатии система берет сгенерированный компенсирующий патч и накатывает его через стандартный транзакционный конвейер деплоя, возвращая узел в эталонное состояние.

### 2.6. Модуль телеметрии и проверки работоспособности (Health-Check)

**Точки контроля:**

| Проверка | Команда | Ожидаемое условие |
|---|---|---|
| Состояние протокола BGP | `show ip bgp summary` | Каждый заявленный сосед в состоянии `Established`, количество принятых префиксов `Prefixes Accepted > 0` |
| Состояние сетевых интерфейсов | `show ip interface brief` | Все физические порты в статусе `up/up` |
| Сквозная сетевая связность | `ping` (серия из 5 ICMP-пакетов до смежных узлов) | Успешная доставка 100% |

**Критерии аварийной деградации сети:**

- переход любой ранее активной сессии BGP в статус `Active`, `Idle` или `Connect`;
- падение физического или протокольного статуса любого интерфейса фабрики (`down/down`);
- потеря более 20% тестовых ICMP-пакетов между узлами фабрики.

> При срабатывании хотя бы одного критерия Post-Check фиксирует аварию, блокирует коммит и инициирует немедленный откат.

### 2.7. Ролевая модель доступа (RBAC)

Для исключения несанкционированных действий со стороны операторов бэкенд поддерживает три уровня привилегий:

| Роль | Права |
|---|---|
| **Viewer** (Наблюдатель) | Просмотр списка устройств, мониторинг топологии, чтение истории запусков задач и просмотр графиков телеметрии |
| **Operator** (Сетевой оператор) | Права роли Viewer плюс запуск холостого прогона (Dry-run), внеочередное сканирование дрейфа и деплой предварительно одобренных конфигураций |
| **Admin** (Сетевой архитектор / Тимлид) | Полный доступ к платформе: изменение параметров инвентаря, утверждение опасных изменений, принудительный накат команд отката и управление учетными записями |

## 4. Организация работы команды

### 4.1. Взаимодействия команды

**Лимиты задач в работе (WIP Limits):**

- В колонке **«В работе»** каждый участник держит строго не более 1 задачи. Нельзя открывать новую задачу, пока текущая не сдана на проверку.
- В колонке **«Проверка / Тест»** одновременно может находиться не более 3 задач на всю команду. Если лимит превышен, разработка новых фич останавливается и все переключаются на ревью и тестирование стенда.

**Ежедневный созвон (Daily Standup):**

- Длительность: **15 минут**.
- Регламент ответов (по 2–3 минуты на человека):
  1. Что конкретно сделал и протестировал за прошедшие сутки?
  2. Какую задачу из бэклога беру в работу на сегодня?
  3. Какие возникли блокеры (что мешает двигаться дальше)?
- Длинные технические споры на созвоне запрещены: при возникновении спорных моментов участники договариваются о точечном созвоне сразу после общего синка.

**Жизненный цикл задачи:**

| Этап | Описание |
|---|---|
| **Бэклог** | Общий пул функциональных требований |
| **Готово к работе** | Задача декомпозирована, есть четкие критерии готовности, назначен один исполнитель |
| **В работе** | Этап активного написания кода или шаблонов |
| **Проверка / Тест** | Создан Pull Request, код протестирован на локальном стенде Containerlab, получен минимум один подтверждающий комментарий от коллеги |
| **Готово** | Код слит в ветку `main`, протестирован в общем контуре, карточка закрыта |

**Критерии готовности задачи (Definition of Done):**

- код проверен линтерами (Ruff, Black) без предупреждений;
- функция протестирована на живом виртуальном стенде с оборудованием Cisco и Arista;
- добавленные эндпоинты задокументированы в OpenAPI/Swagger.
